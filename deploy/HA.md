## 1. 背景与目标

**现状（2026-10-08）**：生产为**单实例**，跑在云主机 `aliyun`（`/opt/ai-gateway-v2`），**存储仍是 SQLite**；PG 版代码在分支 `feature/pg-migration` 待评审合并。切换走**绿地**——先在腾讯云 `tencent`（其 `gw-pg` 容器已跑 PG 16）起 PG 版全栈，用生产快照 `cmd/gwmigrate` 搬运并校验后**切 DNS**，`aliyun`（SQLite）原样留作即时回滚。家主机 `lab` 为潜在备用。**高可用/流复制/自动切换尚未实施**。

**目标**：

## 2. 关键约束与实测事实

### 2.1 硬约束（决定方案能走多远）

1. **存储换 PostgreSQL（D1，代码已实现）**：原「单文件 SQLite，单写者」的天然单点/跨机共享文件不受支持，正是 D1 换 PG 的动因；PG 版代码落地后即解除（多实例可共享同一 PG）。切换前生产仍为 SQLite。
2. **迁移单向**。新二进制把库前向迁移后，**旧二进制读不了新库**（崩溃循环）。→ **回滚必须"换镜像 + 还原库"两件事一起做**。
3. **进程级零停机 + 干净灰度要求"共享状态"** → 需要一个支持多实例并发访问的数据库（PG）。

### 2.2 节点实测

| 节点 | 云 | 公网 IP | 系统 | 规格 | 盘 | docker | `sqlite3` | 目标角色 |
|---|---|---|---|---|---|---|---|---|
| `aliyun` | 阿里云 | 47.116.65.140 | Ubuntu 26.04 | 2C / 1.6G（可用 ~1.2G） | 40G | ✅ 29.1.3 | ❌ | 主（网关 + PG 主） |
| `tencent` | 腾讯云 | 124.223.188.186 | Ubuntu 26.04 | 2C / 1.9G（可用 ~1.4G） | 39G | ✅ 29.1.3 | ❌ | 备（网关 + PG 从） |
| `lab` | 家 | 192.168.0.202 | — | 2C / 5.4G | 48G | ✅ | ❌ | **不纳入**（D3） |

- `aliyun` 与 `tencent` **异云 → 真故障隔离**。
- 两节点公网 IP **不同** → 入口切换需**切域名解析**（用户已确认 **可改解析、可设短 TTL / 健康检查**）。

### 2.3 流量与数据量实测（2026-09-11 → 10-08，27 天）

| 指标 | 实测 | 折算 |
|---|---|---|
| 请求数 | 40,594 | ~1.5k/天 |
| prompt + completion tokens | 125.2M | ~4.6M/天 |
| 代理流量（token × 4B） | ≈ 0.5 GB / 27 天 | — |

## 3. 存储路线（D1）：采用 PostgreSQL（✅ 代码已实现，待合并/切换）

| 维度 | 路线甲：留在 SQLite | **路线乙：PostgreSQL（✅ 已采用，代码已实现）** |
|---|---|---|
| 改动量 | 小 | **大**（`internal/store` 全层重写：方言/迁移/JSON/类型/测试） |
| 不停机 | 节点级蓝绿（客户端视）；单节点自身有秒级窗口 | **真·进程级滚动零停机** |
| 灰度 | 受限（数据分叉） | **干净**（共享库 + 权重路由） |
| 自动切换 | 快照恢复（丢分钟级） | **流复制，RPO ≈ 秒** |
| 数据单点 | DB 文件单点 | 主从，可自动故障转移 |
| 适配规模 | 够 | 够（牛刀，但为 R2/R3/R1 值得） |

**实现要点（`internal/store` 已重写，✅ 代码已实现）**：
- 驱动：`modernc.org/sqlite` → `github.com/jackc/pgx/v5/stdlib`（仍走 `database/sql`：`*sql.DB` / `Scan` / `RowsAffected`）。
- 方言：**源码 SQL 仍写 `?`**，在 `store.go` 的 `pdb`/`ptx` 入口统一重绑为 `$n`（多处 SQL 运行时拼装，占位符数量不定，静态编号不可行）；
  `INTEGER PRIMARY KEY AUTOINCREMENT` → `bigint GENERATED BY DEFAULT AS IDENTITY`；`LastInsertId()` → `RETURNING id`；
  `INSERT OR IGNORE` → `ON CONFLICT ... DO NOTHING`；唯一冲突判定改按 PG SQLSTATE `23505`；
  时间分桶 `substr(datetime(ts,?),1,?)` → `to_char((ts::timestamptz + ?::interval) AT TIME ZONE 'UTC', ?)`；去掉 `PRAGMA`。
- **类型映射保持最小改动（与本节先前的 plan 不同，故更正）**：时间戳**仍 `text`**（UTC RFC3339Nano，**不转 `timestamptz`**）；
  JSON **仍 `text`**（**不转 `jsonb`**）；布尔仍 `bigint` 0/1；金额 `REAL` → `double precision`（**不用 `numeric`**，否则扫不进 `*float64`）。
- 迁移：**单一 PG 基线 DDL**（`internal/store/schema.go` 的 `baselinePG`），`schemaVersion = 14`：首启建 `schema_migrations` 并播版本 14，
  SQLite 时期的 14 步历史迁移**不重放**（后续 PG 迁移从 15 起）。一次性 **SQLite → PG 数据搬运**用 **`cmd/gwmigrate`**
  （逐表逐列原样拷贝 + `setval` 推进 identity 序列 + 逐表 `COUNT(*)` 校验），而非 `pgloader`。
- 并发：SQLite "单写者"假设解除；注意事务隔离与热点更新（钱包/额度）用原子 UPDATE。
- 测试：DB 测试读 **`TEST_PG_DSN`**（未设则 `t.Skip`）；脚手架 `internal/pgtest`（一次一 schema）+ `internal/storetest`；
  `deploy/scripts/test-pg.sh` 起一次性 `postgres:16` 容器跑 `go test ./...`。

> **廉价替代（备选，暂不采用）**：`aliyun` 上两个网关进程**共享同一 SQLite 文件** + 宿主 nginx 健康检查 + 优雅 drain，亦可拿到**真·进程级零停机**而**不重写 store**。约束见 §5.3 附注。若 PG 重写成本过高，可回退到此路。

## 4. 目标架构（路线乙）

```
                        客户端（域名 443）
                              │
                    ┌─────────▼─────────┐
                    │   边缘层（DNS + Nginx/云LB）      │
                    │  · TLS 终结                      │
                    │  · DNS 健康检查 / 短 TTL（R10）   │
                    │  · 权重路由（灰度 R2）            │
                    └────┬───────────────────┬───────┘
                         │                    │
                 ┌───────▼───────┐   ┌────────▼───────┐
                 │ aliyun 网关    │   │ tencent 网关    │   ← 网关无状态，可多实例
                 │ (可多容器滚动)  │   │ (可多容器滚动)   │
                 └───────┬───────┘   └────────┬───────┘
                         │                     │
                 ┌───────▼───────┐   ┌────────▼───────┐
                 │ PostgreSQL 主  │──►│ PostgreSQL 从   │  ← 流复制(RPO≈秒)
                 │ (aliyun)       │   │ (tencent)       │
                 └───────┬───────┘   └────────────────┘
                         │
                 ┌───────▼───────┐
                 │ 备份/PITR      │  pg_basebackup + WAL 归档 → 对象存储(COS)
                 └───────────────┘
```

**组件**：
- **边缘层**：DNS（短 TTL + 健康检查）+ Nginx/云 LB（TLS、权重、故障摘除）。
- **计算层**：网关**无状态化**（状态全在 PG；JWT 本就无状态）→ 可**多实例**、**滚动**、**灰度**。
- **数据层**：**PostgreSQL 主/从**（aliyun 主、tencent 从）；WAL 归档 + `pg_basebackup` 到对象存储做备份。
- **控制层**：`failover`（判活 + 提升从库）、DNS 健康检查。
- **发布层**：expand-contract 迁移纪律（§5.6）+ 容器滚动（§5.3）+ 权重灰度（§5.4）+ 回滚（§5.5）。

## 5. 机制设计

### 5.1 主备与自动切换（R1 / R10）
- **判活信号走独立通道**（不经网关）：主节点定时 push 心跳到备机/对象存储；备侧 controller 判失联即提升。
- **提升动作**：`pg_ctl promote`（PG 从 → 主）→ 切 DNS/边缘权重。可用 **Patroni** 等成熟编排做自动故障转移，或先手动。
- **防脑裂**：① 入口独占（谁是 active 由 DNS+边缘权重唯一决定）；② PG 层可用 quorum/见证（Patroni + etcd/consul，或简化为手动提升）。
- **用户已确认 DNS 可设短 TTL + 健康检查** → **入口级自动摘除**是最低成本、最可靠的一层。

### 5.2 数据复制（D2）
- **PG 流复制**：主 → 从，异步（默认）→ RPO 秒级；如需更强可 `synchronous_commit`（代价：写延迟）。
- **备份**：`pg_basebackup` + WAL 归档（PITR，可恢复到任意时间点）；落对象存储（腾讯 COS）。
- RPO 目标"分钟级"由流复制**超额满足**。

### 5.3 发布模型：真·进程级零停机（R3 / D5）
- 网关**无状态** → 在**同一主机**跑 **N 个网关容器**（共用同一 PG），宿主 nginx/边缘**健康检查 + 优雅 drain**。
- **滚动发布**：逐个替换容器 —— 起新 → 就绪（`/healthz`）→ 接入流量 → 断开旧 → **旧容器排空在途请求后停**。**全程无一颗请求被丢。**
- **迁移前置**：滚动期间新旧实例**并存**，故迁移必须 **expand-contract**（§5.6），否则旧实例读不了新结构。

> **附注（廉价替代）**：若走 SQLite 双进程共享同一文件方案，同样靠宿主 nginx + drain 拿到进程级零停机；但**迁移必须严格仅加列/加表**（不得表重建），且 SQLite 多写者在本机存在写锁争用（此规模无压力）。**因 m0014 属"表重建"，此路对既有迁移不友好** —— 这也是最终选 PG 的原因之一。

### 5.4 灰度发布（R2）
- **PG 共享库** → 新旧实例**读同一份状态**，灰度**不再分叉**。
- 边缘按**权重**把流量分给"灰度实例"（新版本容器）：如 5% → 观察 → 25% → 100%。
- 网关**无状态 JWT** → 无需会话粘性，灰度条件极好。
- 可按令牌/用户维度灰度（把新版本先给你自己的令牌用）。

### 5.5 一键回滚（R4）
- 应用：镜像回退 + 边缘权重切回（容器滚动即可，秒级）。
- 数据：**PG PITR** —— 恢复到升级前时间点（比"还原快照"更强）。
- **发布前强制备份**（`pg_basebackup` 或至少一次逻辑快照）。
- **迁移纪律（§5.6）**：expand-contract 让"应用回滚"不必回滚数据。

### 5.6 迁移安全纪律（R5）
- **expand-contract**：加列/加表（旧实例可忽略）→ 双写/回填 → 切读 → 删旧。**发布期间新旧实例并存，禁止"旧实例读不了"的破坏性迁移。**
- 现状提示：**SQLite → PG 迁移代码已实现（D1，待合并/切换），基线 `schemaVersion = 14`**；旧 SQLite 的 m0013（加列）/ m0014（重建唯一键）属**历史迁移，新 PG 库不重放**。后续 PG 迁移从 **15 起**追加，仍须守 expand-contract（滚动期间新旧实例并存，禁止"旧实例读不了"的破坏性迁移）。

### 5.7 备份与恢复演练（R6）
- 工具：`pg_basebackup` + WAL 归档（PITR）；`KEEP` 轮转；落**异地对象存储**。
- **"备份"≠"能恢复"**：定期**恢复演练**（把备份恢复到 `tencent`/临时库起服务验证）。

### 5.8 可观测与告警（R7 / D4）
- 采集：`/healthz`（含 `version`/`schema`）、容器状态、PG 主从延迟、切换事件、备份成败。
- 告警：**飞书自定义机器人 webhook**（POST JSON）—— 节点不可达、健康校验失败、备份失败、发生切换、复制延迟超阈。
- **前提**：现网 `/healthz` **尚不回 `schema`**（旧格式二进制）→ 升级到新格式后才有此字段。

### 5.9 密钥管理（R8）
- `GW_MASTER_KEY` **全系统唯一、不可再生**（解渠道密钥密文）。
- 要求：进**密码管理器**（离线）；**备份与主密钥分开存放**；两机 `.env` 同值（否则备机解不了数据）；PG 口令另存且不与快照同放。

### 5.10 控制面解耦（R9）
- **恢复动作全部走 `ssh`**（直连两台主机，不经网关）。
- **AI 应急后路**：备一份"绕过本网关"的 Claude 切换（一条命令切 `ANTHROPIC_BASE_URL`/key）→ 网关挂了我仍可用。
- 恢复手册（`RECOVERY.md`）落仓库 **且** 落两台主机本地。

## 6. 资源与预算评估

### 6.1 运行 PostgreSQL 的资源（D1）

| 节点 | 可用内存 | 估占用（PG 调优 + 网关 + Nginx + OS） | 结论 |
|---|---|---|---|
| `aliyun` | ~1.2 G | ≈ 850 M（PG `shared_buffers=256M`） | **可行，偏紧** |
| `tencent` | ~1.4 G | ≈ 850 M | **可行** |

- 库仅 ~17 MB → PG 可调至极小（`shared_buffers=256M`、`work_mem=4M`、`max_connections=50`）。
- **PG 主/从各占一台**会吃掉近半内存；若同机还需跑 Nginx 等需再核。
- 若同机跑多网关容器用于滚动，容器本身很轻（Go 二进制）→ 内存主要给 PG。

### 6.2 流量预算
见 §2.3：**≈ 2~3 GB/月**，对 `tencent` 200GB/月**富余约 60~100 倍**。复制与接管均不构成约束。

### 6.3 磁盘与成本
库 ~17 MB、镜像 ~46 MB、PG 数据 + WAL + 备份若干 → 盘（剩 32G）无压力；COS 存储成本可忽略。

| **P4** | **真·进程级零停机滚动发布** + **权重灰度** + 迁移纪律落地 | R2, R3, R5 | 中 | P3 |
| **P5** | 完整**可观测 + 飞书告警**（延迟/切换/备份/健康） | R7 | 低 | P3 |

> 顺序原则：**P0/P1 成本最低、直接解决"升级出事没退路 + 工具也没了"，且是 P2 的安全网（动 PG 前必须先有当前库的快照）**，先做；**P2（PG 迁移）代码已实现（待合并/切换）**；**下一步重点 = 绿地切换落地 + P3/P4（建立 HA 与发布纪律）**；P5 收敛可观测。

## 9. 风险与开放问题

**风险**：
- **P2 重写量（已化解）**：`internal/store` 全层 + 迁移 + 测试迁移到 PG **代码已实现**；后续 PG 迁移（from 15）仍须配充分测试与数据校验。
- **数据搬运期间的停机（待执行）**：SQLite → PG 一次性搬运（`cmd/gwmigrate` 整库拷贝）已在一次性演练库验证；生产搬运随**绿地切换**执行（tencent 起 PG 版 → `gwmigrate` → 校验 → 冻结窗口终局搬运 → 切 DNS），含短暂停写窗口。
- **首次升级无 `schema` 字段**：现网二进制不回 `schema` → `upgrade.sh` 降级护栏首次会拒（需 `--force`）。
- **PG 单机内存**：2C/1.6~1.9G 跑 PG 需调优，否则易 OOM。
- **密钥同值风险**：两机同 `GW_MASTER_KEY` → 任一机泄露即全泄露。

**已定（§1.1）**：D1 PG（**代码已实现**）、D2 RPO 分钟级、D3 双云不含 lab、D4 飞书、D5 真零停机。

**开放问题**：
1. 后续 PG 迁移（from 15）的**排期**与验收标准（迁移前后数据一致性如何核对？）。
2. PG 自动故障转移用 **Patroni**（重）还是**手动提升**（轻）起步？
3. ~~是否保留 SQLite 双进程方案作为回退预案~~ → **已不适用**（PG 代码已实现）；现成兜底是 `upgrade.sh --rollback`（换镜像 + 还原升级前 PG 快照）。
