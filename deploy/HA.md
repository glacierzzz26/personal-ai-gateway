# 高可用 / 零停机发布方案（HA）

> 定位：本文是 `deploy/DR.md` 的**上位方案** —— 含灾备，并扩展到**零停机发布、灰度、自动切换、回滚**。
> 关系：`DR.md` 仍是一份有效的（但尚未实施的）灾备设计；本文吸收其结论、修正其已过时的拓扑前提，并补齐"发布"这一层。
> 状态：**方案定稿（待人工评审）**。实施按 §8 分阶段推进。

---

## 1. 背景与目标

**现状（2026-10-08 实测）**：生产为**单实例**，跑在云主机 `aliyun`（`/opt/ai-gateway-v2`）；状态为**单文件 SQLite**（`gateway-v2.db`）；家主机 `lab` 与腾讯云 `tencent` 为潜在备用。**当前无备份、无回滚脚本、无高可用**。

**目标**：

| # | 需求 | 来源 |
|---|---|---|
| R1 | 节点/进程挂了 → **自动切换**到备用节点，客户端无感 | 用户 |
| R2 | **灰度发布**（按比例把流量导到新版本） | 用户 |
| R3 | **不停机**发布 | 用户 |
| R4 | **一键回滚**（含库；跨 schema 也对） | 用户 |
| R5 | **迁移安全纪律**（杜绝"旧二进制读不了新库"） | 补全 |
| R6 | **备份 + 恢复演练**（要"恢复得回来"，不只是"有备份"） | 补全 |
| R7 | **可观测 + 告警**（无人盯守也能知道挂了/切了） | 补全 |
| R8 | **密钥管理**（`GW_MASTER_KEY` 唯一不可再生） | 补全 |
| R9 | **控制面解耦**（网关挂了，运维/排查仍可用） | 用户 |
| R10 | **DNS 健康检查**（入口自动摘除坏节点） | 补全 |

**核心场景（用户原话）**：一个节点因升级或故障下线，能切到另一台——**哪怕跑着低版本**——继续服务，**最起码 Claude 能继续工作**。
→ 这条把方案的形状**锚定**为：**活跃-备用（蓝绿）模型 + 备用节点钉在"已知 good 版本"**。备用节点既是故障接管点，**又天然是回滚目标**。

## 2. 关键约束与实测事实

### 2.1 硬约束（决定方案能走多远）

1. **状态 = 单文件 SQLite**，**单写者**。→ 天然单点；跨机共享同一文件不受支持（WAL 不为网络盘设计）。
2. **迁移单向**。新二进制把库前向迁移后，**旧二进制读不了新库**（崩溃循环）。→ **回滚必须"换镜像 + 还原库"两件事一起做**，只换镜像不够。
3. **灰度与"共享状态"存在张力**：两个实例若各持一份库，灰度期间数据分叉（令牌/额度/日志不一致）；若要求强一致，需共享数据库（→ §3 路线乙）。

### 2.2 节点实测

| 节点 | 云 | 公网 IP | 系统 | 规格 | 盘 | docker | `sqlite3` | 现角色 |
|---|---|---|---|---|---|---|---|---|
| `aliyun` | 阿里云 | 47.116.65.140 | Ubuntu 26.04 | 2C / 1.6G（可用 ~1.2G） | 40G | ✅ 29.1.3 | ❌ | **生产主** |
| `tencent` | 腾讯云 | 124.223.188.186 | Ubuntu 26.04 | 2C / 1.9G（可用 ~1.4G） | 39G | ✅ 29.1.3 | ❌ | **备用（本文落点）** |
| `lab` | 家 | 192.168.0.202 | — | 2C / 5.4G | 48G | ✅ | ❌ | 历史备用 |
| `home`-frps | 阿里云 | 47.116.65.140 | — | — | — | — | — | frp 中继 |

- `aliyun` 与 `tencent` **异云 → 真故障隔离**（同区/同账号事故不会同时打掉两台）。
- 两节点公网 IP **不同** → 入口切换需**切域名解析**（用户已确认 **可改解析、可设短 TTL / 健康检查**）。

### 2.3 流量与数据量实测（2026-09-11 → 10-08，27 天）

| 指标 | 实测 | 折算 |
|---|---|---|
| 请求数 | 40,594 | ~1.5k/天 |
| prompt + completion tokens | 125.2M | ~4.6M/天 |
| 代理流量（token × 4B） | ≈ 0.5 GB / 27 天 | — |
| 含 JSON + 流式开销（×3~5） | ≈ 1.5~2.5 GB / 27 天 | **≈ 2~3 GB/月** |
| 库大小 | `gateway-v2.db` 16.9 MB（WAL 4.2 MB） | 缓慢增长 |

## 3. 方案分叉：甲（留 SQLite）vs 乙（换 PostgreSQL）

| 维度 | **路线甲：留在 SQLite** | **路线乙：换 PostgreSQL** |
|---|---|---|
| 改动量 | 小（加脚本 + 边缘层 + 少量代码） | **大**（`internal/store` 全层重写：SQL 方言、迁移、JSON、类型） |
| 不停机 | **客户端可见零停机**（节点级蓝绿，见 §5.3）；单节点自身重启有秒级窗口 | 真·进程级滚动零停机 |
| 灰度 | **受限**：仅"读侧/影子"灰度，写侧因数据分叉不可靠 | 干净支持（共享库 + 权重路由） |
| 自动切换 | 快照 + 近实时同步，RPO 分钟级 | 主从流复制，RPO ≈ 0 |
| 数据单点 | DB 文件仍单点（靠复制兜底） | 可多副本 / 自动故障转移 |
| 适配现网规模 | ✅ 完全够（17MB 库、轻流量） | 够，但**杀鸡用牛刀** |

**推荐**：**先走甲**，把"可靠底座"（备份 / 回滚 / 蓝绿切换 / 自动接管 / 迁移纪律）做出来——这直接覆盖 R1/R4/R6/R9 与 R3 的**客户端视角**。**把乙（PG）留作 P5 可选**，只在"确需真·进程级零停机或干净灰度"时再上；届时的动因、资源与迁移路径见 §6 / §8。

> 依据：R2 干净灰度与 R3 真·进程级零停机都需要共享状态；但当前**轻流量 + 用户对 RPO 的容忍（"切到低版本继续用即可"）**决定甲已满足核心诉求，乙的收益不抵其重写成本。

## 4. 目标架构（路线甲）

```
                        客户端（域名 443）
                              │
                    ┌─────────▼─────────┐
                    │   边缘层（DNS + Nginx/云LB）      │
                    │  · TLS 终结                      │
                    │  · DNS 健康检查 / 短 TTL（R10）   │
                    │  · 权重路由（蓝绿/灰度 R2）       │
                    └────┬───────────────────┬───────┘
                         │ 主(权重100)        │ 备(权重0/切换时100)
                         ▼                    ▼
                 ┌──────────────┐     ┌──────────────┐
                 │ aliyun 网关   │     │ tencent 网关  │  ← 钉在"已知 good 版本"
                 │ (新版本)      │     │ (旧版本/回滚源)│
                 └──────┬───────┘     └──────┬───────┘
                        │ SQLite(WAL)         │ SQLite(恢复自快照)
                        ▼                     ▲
                 ┌──────────────┐             │
                 │  Litestream   │──WAL 推送──►│  对象存储(腾讯 COS / S3 兼容)
                 │  (连续复制)    │─────────────┘
                 └──────┬───────┘
                        │ 心跳(独立通道)
                        ▼
                 ┌──────────────┐
                 │ failover ctrl │  判活 → 切 DNS/权重 → 提升备机
                 └──────────────┘
```

**组件**：
- **边缘层**：DNS（短 TTL + 健康检查）+ Nginx/云 LB（TLS、权重、故障摘除）。
- **计算层**：2+ 网关实例。网关用**无状态 JWT**（HS256），**无需会话粘性** → 对蓝绿/灰度极友好。
- **数据层**：SQLite + **Litestream**（连续 WAL 推送至 S3 兼容对象存储，腾讯云用 **COS**；恢复即最新快照）。（路线乙时换 PG 主从。）
- **控制层**：`failover`（心跳判活 + 提升备机）、DNS 健康检查。
- **发布层**：迁移纪律（§5.6）+ 蓝绿切换（§5.3）+ 自动回滚（§5.5）。

## 5. 机制设计

### 5.1 主备与自动切换（R1 / R10）
- **判活信号走独立通道**（不经网关）：主节点定时 push 心跳到备机/对象存储；备侧 controller 判失联即提升。
- **提升动作**：备机 `Litestream restore` 到最新 → 起网关 → 切 DNS/边缘权重。
- **防脑裂**：① 端口/入口独占（谁是 active 由 DNS+边缘权重唯一决定）；② 或对象存储租约（备机提升前先抢租约）。误判两方向都无害（对齐 `DR.md §3`）。
- **用户已确认 DNS 可设短 TTL + 健康检查** → 可做**入口级自动摘除**，这是最低成本、最可靠的一层。

### 5.2 数据复制（R6 基础）
- **首选 Litestream**：连续把 WAL 增量推到对象存储（腾讯 COS，S3 兼容 API）。RPO = 推送间隔（秒~分钟）。
- 备机以"**持续 restore**"跟到近实时；提升时无需等待（已就绪）。
- 备选：定期快照（`backup.sh`）+ 定时推送（更简单，RPO 更大）。**先做备选，再升级到 Litestream。**

### 5.3 发布模型：节点级蓝绿 = 客户端零停机（R3）
> 这是路线甲拿到"客户端可见零停机"的关键，也是直接满足用户核心场景的机制。

**发布步骤（逐节点、永不停所有节点）**：
1. 备节点（`tencent`）当前跑**已知 good 版本**，数据同步到近实时。
2. **先把流量切到备节点**（边缘权重/DNS）—— 此时客户端仍被服务（可能丢最后几秒~几分钟写入，在容忍内）。
3. 在主节点（`aliyun`）**发布新版本**（迁移 + 重启）—— 主节点此刻**无流量**，其重启对客户端**不可见**。
4. 校验新版本健康（`/healthz` 的 `version` + `schema`）。
5. **把流量切回主节点**，并把故障窗口内落在备节点的写入**对账回并**（对齐 `DR.md §3` 的 `handback` 思路）。
6. 重复（可选）升级备节点到新版本。

→ **客户端全程被某个健康节点服务 ⇒ 客户端视角零停机**。代价：切换窗口内的**数据分叉**（靠 step 5 对账），以及"单节点自身仍有秒级重启窗口"（对客户端不可见）。

### 5.4 灰度发布（R2）
- **在路线甲下是受限的**：干净灰度要求新旧版本**读同一份状态**。两实例各持一份 SQLite → 写侧分叉，不可靠。
- **可做的**：① **影子/只读灰度**（新版本只接读流量观察）；② **按用户/令牌路由**且明确接受目标用户的写入落单一节点（复杂度高）；③ **`lab`/`tencent` 内部先自用**——把新版本先给"你自己的令牌"用，观察无误再全量（**最实用的"人肉灰度"**）。
- **干净灰度留待路线乙（PG）**。

### 5.5 一键回滚（R4）
- `upgrade.sh --rollback`：换回镜像 **且** 还原升级前库快照（跨 schema 的唯一正确路径）。
- **发布前强制快照**（`upgrade.sh` 已设计）。
- **蓝绿模型的额外好处**：备节点本就跑"已知 good 版本"，**切过去即回滚**（R4 与 R1 共用一条路径）。

### 5.6 迁移安全纪律（R5）
- **expand-contract**：加列/加表（旧版可忽略）→ 双写/回填 → 切读 → 删旧。**任何发布禁止"旧二进制读不了新库"的破坏性迁移。**
- 现状提示：`dev` 线的 m0013（加 `cache_write_price`）+ m0014（重建唯一键为 `(provider, model_name, source)`）**属加列/重建，可控**；但**生产仍停在 m0012，一次要跳两级**——正是**必须先在 P1 拍快照**的场景。

### 5.7 备份与恢复演练（R6）
- `backup.sh`（现网无 `sqlite3` → 走"停容器几秒"分支）+ `KEEP` 轮转。
- **"备份"≠"能恢复"**：定期做**恢复演练**（把快照恢复到 `tencent`/临时目录起服务验证）。
- 备份落**异地**（对象存储），避免与主机同故障域。

### 5.8 可观测与告警（R7）
- 采集：`/healthz`（含 `version`/`schema`）、容器状态、切换事件、备份成败。
- 告警：节点不可达、健康校验失败、备份失败、发生切换 → 推送（企业微信/邮件/短信任选其一）。
- **前提**：现网 `/healthz` **尚不回 `schema`**（旧格式二进制）→ 首次升级到新格式后才有此字段。

### 5.9 密钥管理（R8）
- `GW_MASTER_KEY` **全系统唯一、不可再生**（解渠道密钥密文）。
- 要求：进**密码管理器**（离线）；**快照与主密钥分开存放**（不可同放一台备机）；`tencent` 的 `.env` 与 `aliyun` **同值**（否则备机解不了数据）。

### 5.10 控制面解耦（R9）
- **恢复动作全部走 `ssh`**（直连两台主机，不经网关）→ 网关死不死都能操作。
- **AI 应急后路**：备一份"绕过本网关"的 Claude 切换（一条命令切 `ANTHROPIC_BASE_URL`/key 到官方或第二通道）→ 网关挂了我仍可用。
- 恢复手册（`RECOVERY.md`）落仓库 **且** 落两台主机本地。

## 6. 资源与预算评估

### 6.1 能否跑 PostgreSQL（路线乙的前置）

| 节点 | 可用内存 | 估占用（PG 调优 + 网关 + Nginx + OS） | 结论 |
|---|---|---|---|
| `aliyun` | ~1.2 G | ≈ 850 M（PG `shared_buffers=256M`） | **可行，偏紧** |
| `tencent` | ~1.4 G | ≈ 850 M | **可行** |

- 库仅 17 MB → PG 可调至极小（`shared_buffers=256M`、`work_mem=4M`、`max_connections=50`）。
- **PG 主 + 从各占一台**会吃掉近半内存；若同时还要跑 Nginx/其它服务需再核。
- **结论**：**资源上能跑**，但路线甲当前不需要 —— 乙仅在有明确收益（真零停机/干净灰度）时上。

### 6.2 流量预算
见 §2.3：**≈ 2~3 GB/月**，对 `tencent` 200GB/月**富余约 60~100 倍**。复制与接管均不构成约束。

### 6.3 磁盘与成本
库 17 MB、镜像 ~46 MB、备份若干 → 盘（剩 32G）无压力；COS 存储成本可忽略。

## 7. 架构决策记录（ADR 摘要）

| # | 决策 | 理由 |
|---|---|---|
| AD-1 | 先走**路线甲（SQLite）**，PG 列为 P5 | 覆盖核心诉求且成本低；重写 store 风险高、收益当前不足 |
| AD-2 | 备用节点**钉在已知 good 版本**，**不自动跟升级** | 满足"切到低版本仍可用"；并天然充当回滚目标；防"坏版本被 HA 复制到所有副本" |
| AD-3 | 以**节点级蓝绿**实现客户端零停机 | SQLite 下唯一能达到"客户端不可见"的发布模型 |
| AD-4 | 数据复制先用**定期快照**，再升级到 **Litestream** | 先落地、再逼近 RPO |
| AD-5 | **备份与主密钥分开存放**；`GW_MASTER_KEY` 两台同值 | 安全 + 备机可用 |
| AD-6 | 迁移强制 **expand-contract** | 杜绝旧二进制读新库 |
| AD-7 | 恢复走 **ssh + 手册**，不依赖网关/AI | 控制面与数据面解耦 |

## 8. 分阶段路线

| 阶段 | 交付 | 解锁需求 | 成本/风险 | 依赖 |
|---|---|---|---|---|
| **P0** | `RECOVERY.md` 手册（升级前快照 / 回退两步 / 切机 / AI 应急切换）+ Claude 应急切换脚本 | R9 | **0** | — |
| **P1** | `aliyun` 装 `upgrade.sh`/`backup.sh` + **首份快照** + **副本影子演练**（验证 m0012→m0014） | R4, R6 | 低 | P0 |
| **P2** | `tencent` 预置备机栈（compose + 证书 + 同主密钥 `.env`）+ **快照推送** + `failover.sh`（手动）+ DNS 切换 | R1(半), R10 | 中 | P1 |
| **P3** | 心跳 + 自动接管 controller（+ 切回对账 `handback`） | R1(全) | 高（脑裂） | P2 |
| **P4** | **节点级蓝绿发布**流水线 + 迁移纪律落地 + 告警 | R2(实用), R3(客户端视), R5, R7 | 中 | P2 |
| **P5**（可选） | 切换存储为 **PostgreSQL**（主从） | R2(干净), R3(进程级) | **大** | 需求明确后评估 |

> 顺序原则：**P0/P1 成本最低、直接解决"升级出事没退路 + 工具也没了"**，先做；P2/P3 落在 `tencent`；P4 建立发布纪律；P5 视需要。

## 9. 风险与开放问题

**风险**：
- **数据分叉**：蓝绿切换窗口内的写入会分叉（靠 `handback` 对账），是路线甲的核心代价。
- **脑裂**：自动接管（P3）需租约/端口独占防线；误判两方向已设计为无害。
- **首次升级无 `schema` 字段**：现网二进制不回 `schema` → `upgrade.sh` 降级护栏首次会拒（需 `--force`）；升级到新格式后恢复正常。
- **密钥同值风险**：两机 `.env` 同 `GW_MASTER_KEY` → 任一机泄露即全泄露；需配合"快照+密钥分开存放"。

**开放问题（待用户拍板）**：
1. 零停机**硬性程度**：接受"节点级蓝绿（客户端视零停机）"，还是**必须进程级零停机**（→ 触发 P5）？
2. RPO 目标：**秒级**（Litestream）/ **分钟级**（定期快照）/ **≤15min**？
